## 0. Контекст проекта (сверка с ТЗ)

**Pulse** — real-time media monitoring pipeline. Пользователь создаёт «монитор»
с ключевыми словами → система собирает публикации из открытых источников
(первый источник — Hacker News) → фильтрует → лента + полнотекстовый поиск + график упоминаний.

Стек (зафиксирован ТЗ, здесь не пересматривается):

| Слой | Технологии |
|---|---|
| Ингестор | Go, Gin, kafka-go, gofeed |
| Шина | Kafka |
| Обработчик | Python 3.12, aiokafka, Pydantic, Dishka |
| Хранение/поиск | ElasticSearch (PostgreSQL **не используется** — осознанное решение) |
| Кэш | Redis |
| API | FastAPI |
| Фронт | React, TypeScript, Redux Toolkit |
| Инфра | Docker, k3d + Helm, GitHub Actions → ghcr.io |
| Тесты | pytest + testcontainers, coverage ≥ 90% |

Методология: **вертикальные срезы**. Первый срез — сквозной прогон
HN → Kafka → ES → поиск. Definition of Done каждого среза включает замеры
(событий/сек, латентность поиска до/после кэша).

## 1. Системный уровень: event-driven архитектура

### 1.1. Что такое event-driven (EDA)

Компоненты общаются не прямыми вызовами («сделай X»), а **событиями** — фактами
о том, что уже произошло («появилась публикация»). Отправитель объявляет факт
и не знает, кто и как отреагирует.

Ключевое свойство — **инверсия зависимости**: при прямом вызове ингестор должен
знать адрес и API обработчика; при событиях — только «канал». Слушателей может
быть 0, 1 или N, и они добавляются без изменения отправителя.

EDA не равно «брокер сообщений». Уровни, где EDA живёт в Pulse:

1. **Между сервисами** — Kafka (нужны durability, буферизация, replay).
2. **Внутри Python-обработчика** — asyncio event loop (события readiness от ОС: epoll).
3. **На фронте** — DOM events, Redux actions (action — это, по сути, событие).

### 1.2. Event vs Command

| | Event (событие) | Command (команда) |
|---|---|---|
| Семантика | «Произошло X» (прошлое) | «Сделай X» (императив) |
| Кто главный | Отправитель не знает получателей | Отправитель ожидает конкретного исполнителя |
| Имя | `item.published`, `post.ingested` | `IndexDocument`, `CreateMonitor` |
| Отказ получателя | Не проблема отправителя | Ошибка, которую надо вернуть |

В Pulse: сообщения в Kafka — **события** (`raw_items`: «источник опубликовал элемент»).
HTTP-запросы к FastAPI (`POST /monitors`) — **команды**.
Не смешивать: в Kafka не кладём «команды обработчику», кладём факты.

### 1.3. Топология потока данных

```
HN API → [Go ingestor] → Kafka(topic: raw_articles) → [Python processor] → ES(index: articles)
                                                                        ↘ (метрики)
Пользователь → [React] → [FastAPI] → Redis (cache) → ES (поиск/агрегации)
```

Решения (в соответствии с §3.2 ТЗ):

- **Один топик `raw_articles` на все источники** (пока их мало), а не топик-на-источник.
  В сообщении есть поле `source`. Причина: меньше операционного шума, consumer group
  одна. Пересмотр — когда источников станет >5 или у них радикально разный трафик.
  (Топик `matched_articles` — расширение после MVP, если появится второй консьюмер.)
- **Ключ партиционирования** — `source_id` (по ТЗ): все версии одного элемента
  попадают в одну партицию → сохраняется порядок внутри источника.
- **Число партиций** — 3 (по ТЗ), retention 24h. Партиция — единица параллелизма
  консьюмеров; больше консьюмеров, чем партиций, — простаивают.

### 1.4. Гарантии доставки и идемпотентность (критично!)

Kafka в стандартной конфигурации consumer'а даёт **at-least-once**: сообщение может
быть обработано повторно (rebalance, падение до commit оффсета). Отсюда правило:

> **Обработчик обязан быть идемпотентным.** Повторная обработка того же сообщения
> не должна создавать дубликат.

Реализация в Pulse — **естественная дедупликация через детерминированный `_id` в ES**
(по §4.2 ТЗ):

```
doc_id = sha256(f"{source}:{source_id}")           # напр. sha256("hackernews:38912345")
es.index(index="articles", id=doc_id, document=doc)   # index = upsert
```

Повторная запись перезапишет тот же документ — дубликата нет. Это снимает
необходимость в exactly-once semantics (transactions Kafka), которые для
этого проекта — overkill.

### 1.5. Порядок commit'а оффсетов (Unit of Work на уровне консьюмера)

Инвариант: **оффсет коммитится только после успешной записи в ES.**

```
poll batch → validate (Pydantic) → bulk index в ES → commit offsets
```

- `enable.auto.commit = false` в aiokafka, ручной `commit()` после bulk.
- Если ES упал посреди батча — оффсет не коммитим, батч переобработается
  (идемпотентность из 1.4 делает это безопасным).
- Graceful shutdown: по SIGTERM — дообработать текущий батч, закоммитить, выйти.
  Это же требование Kubernetes (preStop / terminationGracePeriodSeconds).

### 1.6. Обработка «ядовитых» сообщений (Dead Letter Queue)

Сообщение, которое невозможно распарсить/провалидировать, не должно блокировать
партицию бесконечными ретраями.

Политика Pulse (DLQ в ТЗ не описан — это дополнение теории; при внедрении добавить в ADR):
- Ошибка **валидации** (битый JSON, не проходит Pydantic) → лог с payload'ом +
  публикация в топик `raw_articles.dlq` → skip + commit. Ретраи бессмысленны.
- Ошибка **инфраструктуры** (ES недоступен) → ретрай с экспоненциальным backoff,
  оффсет не коммитим. Ретраи осмысленны.

Различение «ошибка данных» vs «ошибка среды» — ключевой принцип: первые скипаем
в DLQ, вторые ретраим.

### 1.7. Backpressure

Kafka сама является буфером: если обработчик медленнее ингестора, растёт **consumer lag**
(метрика №1 для алертов), но система не падает. Ингестор не должен ждать обработчик —
в этом весь смысл шины. Мониторим lag, масштабируем консьюмеров (до числа партиций).

## 2. CQRS-lite: разделение путей записи и чтения

Полноценный CQRS (отдельные модели, event sourcing) — не нужен. Но **пути записи
и чтения в Pulse физически разные**, и это надо понимать как осознанный паттерн:

- **Write path**: HN → Go → Kafka → Python → ES. Оптимизирован под throughput
  (bulk indexing, батчи).
- **Read path**: React → FastAPI → Redis → ES. Оптимизирован под latency
  (кэш, готовые агрегации).

Следствия:
- **Eventual consistency**: между «HN опубликовал» и «видно в поиске» есть лаг
  (секунды). Это нормально и должно быть отражено в UI (нет кнопки «обнови прямо сейчас»).
- ES `refresh_interval` (по умолчанию 1s) — ещё один источник лага: документ после
  index не мгновенно searchable. Не крутить `refresh=true` на каждую запись — убивает
  производительность; в тестах — да, в проде — нет.

## 3. Паттерны Python-обработчика и API

### 3.1. Repository

Весь доступ к ES и Redis — за интерфейсами (Protocol/ABC). Бизнес-логика не
импортирует `elasticsearch` и `redis` напрямую.

```python
class ArticleRepository(Protocol):
    async def bulk_upsert(self, articles: list[Article]) -> None: ...
    async def search(self, query: SearchQuery) -> SearchResult: ...

class ElasticArticleRepository:   # реализация
    def __init__(self, client: AsyncElasticsearch): ...
```

Зачем в проекте без ORM: (1) тестируемость — в unit-тестах подставляется fake,
testcontainers оставляем для интеграционных; (2) вся ES-специфика (DSL-запросы,
маппинги) в одном месте; (3) на собеседовании это разбираемый артефакт.

Анти-цель: не строить «универсальный generic repository» — только методы,
которые реально нужны use case'ам.

### 3.2. Dependency Injection (Dishka)

Правило: **код зависит от абстракций, контейнер собирает конкретику.**

- Провайдеры Dishka создают: конфиг → клиенты (ES, Redis, Kafka) → репозитории → сервисы.
- Scopes: `APP` для клиентов/пулов (живут всё время процесса),
  `REQUEST` для объектов на один HTTP-запрос / один батч сообщений.
- FastAPI-хендлеры получают зависимости через интеграцию Dishka, не через
  глобальные переменные и не через `Depends(get_es_client)` руками.
- В тестах контейнер пересобирается с подменёнными провайдерами — так достигается
  coverage ≥90% без моков-заплаток по всему коду.

Композиционный корень (composition root) — один: точка входа сервиса. Никаких
`container.get()` из глубины бизнес-логики (это уже Service Locator — антипаттерн).

### 3.3. DTO + Anti-Corruption Layer (Pydantic на границах)

Три слоя моделей, не смешивать:

1. **Внешняя схема источника** (`HNItemRaw`) — как HN реально отдаёт данные,
   со всеми их странностями (опциональные поля, unix-время).
2. **Внутреннее каноническое событие** (`RawArticle`) — единая схема сообщения в Kafka
   для всех источников. Это **контракт** между Go и Python.
3. **Документ ES / API-ответы** (`ArticleDoc`, `SearchResponse`) — форма хранения и выдачи.

Anti-corruption layer — это преобразование 1 → 2 на стороне ингестора: кривизна
внешнего API не протекает дальше границы. Новый источник = новый маппер, ядро не меняется.

**Контракт Kafka-сообщения** — ровно §4.1 ТЗ, источник правды там:

```json
{
  "source": "hackernews",
  "source_id": "38912345",
  "url": "https://...",
  "title": "…",
  "body": "…",
  "author": "…",
  "published_at": "2026-07-03T10:00:00Z",
  "fetched_at": "2026-07-03T10:00:05Z"
}
```

Правила эволюции контракта: новые поля — только опциональные (backward compatible).
Поле `schema_version` в ТЗ отсутствует; добавлять только при первом breaking change
(и зафиксировать это в ADR + обновить §4.1 ТЗ). Schema Registry — overkill для pet-проекта.

### 3.4. Cache-Aside (Redis)

Единственный паттерн кэширования в проекте (write-through/write-behind не используем):

```
GET /search?q=… :
  key = "search:" + hash(нормализованный запрос)
  hit  → вернуть из Redis
  miss → запрос в ES → положить в Redis с TTL → вернуть
```

Решения:
- **TTL 30–60 сек** вместо инвалидации. Данные append-only и eventual consistent
  по своей природе — короткий TTL честнее и на порядок проще, чем точечная инвалидация.
- **Нормализация ключа**: сортировка параметров, lower-case запроса — иначе
  `q=go&page=1` и `page=1&q=go` дадут два ключа.
- **Что кэшируем**: сериализованный готовый ответ API (JSON), а не сырой ответ ES.
- **Отказ Redis ≠ отказ сервиса**: try/except вокруг кэша, при недоступности Redis
  идём напрямую в ES (graceful degradation). Кэш — оптимизация, не зависимость.
- Метрика hit rate — обязательна (это одна из цифр DoD: латентность до/после кэша).

Известная проблема — **cache stampede** (истёк горячий ключ → толпа запросов в ES).
Для Pulse достаточно знать о ней и упомянуть; решение (lock / early recompute)
внедряем только если замеры покажут проблему.

### 3.5. Сервисный слой (use cases)

Между FastAPI-роутером и репозиториями — тонкий сервисный слой:
`SearchService.search(query)` — оркестрация «кэш → репозиторий → метрики».
Роутер: распарсить запрос → вызвать сервис → отдать ответ. Никакой логики в роутерах,
никакого HTTP в сервисах. Это то, что реально тестируется unit-тестами.

### 3.6. Настройки

Pydantic Settings, конфиг только из env (12-factor). Никаких `config.py` с ветвлением
по окружениям — окружения различаются значениями env-переменных (Helm values), не кодом.

## 4. Паттерны Go-ингестора

### 4.1. Pipeline из горутин

```
[poller] --ch--> [mapper: HNItemRaw → RawItem] --ch--> [publisher → Kafka]
```

- Стадии соединены каналами; каждая стадия — отдельная ответственность.
- **Отмена через `context.Context`** — контекст пронизывает весь pipeline,
  по SIGTERM отменяем корень, стадии дочищают буферы и выходят (graceful shutdown).
- Ошибки не роняют процесс: логируются, элемент скипается, poller продолжает.

### 4.2. Poller: вежливый опрос внешнего API

- Интервальный опрос HN API (у HN нет push).
- **Экспоненциальный backoff с jitter** при ошибках: 1s → 2s → 4s → … cap 60s.
  Jitter обязателен — иначе синхронные ретраи создают волны.
- **Rate limiting** исходящих запросов (token bucket, `golang.org/x/time/rate`).
- **Watermark**: помним `max(external_id)` последнего забранного элемента, чтобы
  не перечитывать всё. Хранится в памяти + допустимо терять при рестарте
  (перечитаем хвост — идемпотентность в ES это поглотит). Это осознанный трейд-офф:
  не тащим отдельное хранилище состояния в ингестор.

### 4.3. Publisher

- `kafka-go` writer c `RequiredAcks = all` — не терять события на этапе публикации.
- Ключ сообщения = `source:external_id` (см. 1.3).
- Ретраи публикации с backoff; если Kafka лежит долго — poller естественно
  тормозится через заполненные каналы (встроенный backpressure каналов Go).

### 4.4. Gin

Только служебные endpoint'ы: `/healthz` (liveness), `/readyz` (readiness — проверка
коннекта к Kafka), `/metrics`. Никакой бизнес-логики по HTTP в ингесторе.

## 5. ElasticSearch: моделирование

- **Один индекс `articles`**, документ = публикация. `_id = sha256(source:source_id)` (см. 1.4).
- **Явный маппинг** (не полагаться на dynamic mapping, база — §4.2 ТЗ):
  - `title`, `body` → `text` с анализатором `standard` (расширение: language-specific),
  - `source`, `author`, `lang` → `keyword`,
  - `matched_monitor_ids` → `keyword` (массив),
  - `published_at`, `fetched_at` → `date`,
  - `url` → `keyword` (по URL не ищем full-text).
- Поиск: `multi_match` по `title^2, body` (буст заголовка).
- График упоминаний: `date_histogram` агрегация по `published_at` + фильтр.
- **Матчинг мониторов — на записи** (по ТЗ): processor сопоставляет статью с ключевыми
  словами активных мониторов и пишет `matched_monitor_ids` в документ. Лента монитора
  (`/feed`) — это дешёвый term-запрос по `matched_monitor_ids`, а не полнотекстовый
  поиск на каждое открытие ленты.
  - **Следствие (важно понимать!):** новый или изменённый монитор автоматически видит
    только *будущие* статьи. Ретроспектива — через `/search` (полнотекст по архиву) или
    через backfill-задачу (`update_by_query` в ES) — backfill вне MVP.
  - Значит, processor'у нужен доступ к списку активных мониторов: читать из индекса
    `monitors` с периодическим обновлением (кэш в памяти + TTL ~30 сек) — MVP-решение.
    Расширение по ТЗ: percolate queries в ES.
- Мониторы хранятся в ES-индексе `monitors` (или Redis — оба варианта допустимы по ТЗ).
- Пагинация: `from/size` до 10k; если понадобится глубже — `search_after`, не scroll.

## 6. Тестирование (пирамида)

| Уровень | Что | Чем |
|---|---|---|
| Unit | сервисы, мапперы, нормализация ключей кэша | fake-репозитории через DI |
| Интеграционные | реальные ES/Redis/Kafka | **testcontainers** |
| E2E (по срезу) | HN-fixture → Kafka → processor → ES → API отвечает | docker compose / testcontainers |

Принципы:
- Контейнер DI пересобирается в тестах — никаких monkeypatch внутренностей.
- Интеграционный тест идемпотентности обязателен: одно сообщение дважды → в ES один документ.
- Тест DLQ: битое сообщение → попало в `raw_items.dlq`, поток не остановился.
- В тестах ES можно `refresh=true`/`refresh("wait_for")` — в проде нельзя (см. §2).
- Coverage ≥90% — по Python-сервисам; Go — стандартный `go test` + happy-path интеграционный.

## 7. Инфраструктура и деплой

- **Docker**: multi-stage build (Go — scratch/distroless; Python — slim + uv/pip).
- **k3d + Helm**: один umbrella-чарт или чарт-на-сервис; конфиги через values +
  env (см. 3.6). Kafka/ES/Redis в dev — через готовые чарты.
- **Пробы**: liveness ≠ readiness. Readiness проверяет зависимости (Kafka/ES доступны),
  liveness — только «процесс жив». Не проверять зависимости в liveness — иначе
  падение ES перезапускает здоровые поды каскадом.
- **Graceful shutdown повсюду**: SIGTERM → дообработать → закоммитить → выйти
  (см. 1.5, 4.1) + `terminationGracePeriodSeconds` с запасом.
- **CI (GitHub Actions)**: lint → unit → integration (testcontainers) → build →
  push в ghcr.io. Теги образов = git sha (+ semver на релизы).
- **Метрики DoD**: событий/сек через pipeline; p50/p95 латентность `/search`
  до и после включения кэша; consumer lag. Замеры — часть Definition of Done среза.

## 8. Фронт (кратко, для полноты)

- Redux Toolkit + RTK Query для запросов к API — кэширование и инвалидация на клиенте
  «из коробки», не писать fetch-обвязку руками.
- Состояние сервера (результаты поиска) — в RTK Query; состояние UI (открытые панели,
  текущий монитор) — в обычных slice'ах. Не смешивать server state и client state.
- Дебаунс поискового ввода (300 мс) — чтобы не бомбить API на каждый символ.

## 9. Осознанные упрощения (anti-scope)

Зафиксировано, чтобы не спорить с собой в процессе:

- **Нет PostgreSQL** — ES покрывает и хранение, и поиск. Мониторы пользователя
  на MVP-этапе — документы в ES (индекс `monitors`) или Redis.
- **Нет exactly-once / Kafka transactions** — идемпотентность дешевле и достаточна.
- **Нет Schema Registry и нет `schema_version`** — до первого breaking change.
- **Нет точечной инвалидации кэша** — TTL 30–60 сек (по ТЗ).
- **Нет backfill'а лент** — новый монитор матчится только с будущими статьями;
  ретроспектива через `/search`.
- **Нет percolate queries** — простой матчинг по подстроке/word-boundary (MVP по ТЗ).
- **Нет авторизации/мультитенантности** в первых срезах.
- **Нет autoscaling/HPA** — ручное масштабирование консьюмеров.

Каждое из упрощений — потенциальный ответ на собеседовании в формате
«знаю полное решение, осознанно выбрал простое, вот критерий пересмотра».

## 11. Словарь терминов (для собеседований)

- **EDA** — архитектура на событиях-фактах; инверсия зависимости отправитель/получатель.
- **Event vs Command** — факт в прошлом vs императив конкретному исполнителю.
- **At-least-once** — гарантия «доставим хотя бы раз», требует идемпотентности.
- **Идемпотентность** — повтор операции не меняет результат.
- **Consumer lag** — отставание консьюмера от конца топика; главная метрика здоровья.
- **DLQ** — «карантин» для ядовитых сообщений.
- **CQRS** — разные пути/модели для записи и чтения.
- **Eventual consistency** — данные сойдутся «в итоге», не мгновенно.
- **Cache-aside** — приложение само управляет кэшем: miss → источник → put.
- **Cache stampede** — толпа запросов в источник при истечении горячего ключа.
- **Repository** — абстракция доступа к хранилищу, изолирует инфраструктуру.
- **DI / composition root** — зависимости собираются в одной точке входа.
- **Service Locator (антипаттерн)** — `container.get()` из глубины кода.
- **Anti-corruption layer** — маппер на границе, не пускающий чужую схему внутрь.
- **Backpressure** — механизм торможения производителя под скорость потребителя.
- **Graceful shutdown** — дообработать и зафиксировать состояние перед выходом.
- **Liveness vs readiness** — «жив ли процесс» vs «готов ли принимать трафик».
